# 0028. Running the tests and looking for a fix from the desktop app

## Context

The desktop app can choose the project (ADR 0027), but to see the tests run or to look for a fix it was still necessary to open a terminal. This is the second step of stage 2 of the app. The third is reviewing a fix and applying it with a confirmation in the app's own window, and it comes after this one.

Two things make this step different from the earlier ones. Looking for a fix may ask Claude for patches, which spends tokens, and a run can take minutes, so it has to be possible to stop it.

## Decision

- **A section of the menu, Fix, with two buttons and a stop button.** **Run the tests** and **Look for a fix**. While something runs, the card says so, the buttons give way to **Stop**, and what the system prints is shown below, line by line, as it is printed. The result is told in a message that can be closed. It stays when changing section, and goes when the project changes, because it was about the other project.
- **It uses the system's own commands, inside the cli container, and no new code of the system.** `docker compose exec -T cli healer test`, and `healer run --no-apply --save /data/healer/fix.json`. The exit codes are read as the commands define them: `healer test` returns 0 when the tests pass and 1 when they fail, `healer run` returns 0 when it fixed the tests or there was nothing to fix, and 1 when it did not find a fix. Anything else is an error, and its `error:` line is shown. Output is not buffered (`PYTHONUNBUFFERED`), or it would arrive at the end.
- **Nothing is written to the project.** `--no-apply` makes `healer run` skip the question about applying, and the patch is saved in the data volume, not in the project's folder. Each search replaces the saved patch. The bridge functions take no argument and the handlers ignore what the page sends: the page cannot give a command, a path or an option.
- **The user is asked before Claude may be used, by the main process, in a dialog of the app.** The question is not a button of the page, because a page that is wrong or compromised could press it. The dialog says that Claude may be asked for patches with the key, that this spends tokens, that a fix stored here or from the team is tried first and costs nothing, and that the files are not changed. **Cancel** is the default button and the one Escape answers. It is not asked when the services have no key, because then nothing can be spent. Declining runs nothing.
- **It runs only when it can mean what it says.** The services must be running, and the cli container must have the folder chosen in Project. Otherwise it says what is missing, in the message, and asks nothing. One run at a time.
- **The output is cleaned before the page sees it.** Anything shaped like an Anthropic key is replaced by `[hidden]`, and a line is cut at 2,000 characters. The page keeps the last 200 lines. The app does not hold the key while it runs: it is in the container's environment.
- **The advice of the system about the key is told the app's way.** The system says to add the key to `.env` and recreate the container; the app keeps the key in the secret store and gives it to the services when they restart, so the message says to save it in Settings and restart the services.
- **Stopping goes inside the container, and frees the sandbox.** Both were checked with the real system:
  - Killing the `docker compose exec` client does not stop what it started in the container: a `sleep` was still running after its client was killed. So the program is started by a shell that writes its process id to a file and then becomes the program, and Stop sends it the signal of Ctrl+C from a second `exec`, trying again for a moment if the file is not written yet. The file is removed when the run ends.
  - The test sandbox answers one request at a time and does not notice that the cli left. After a stop, its `pytest` was still running 12 seconds later, and it would go on until the tests ended or reached their own limit (300 seconds by default), and the next run would wait behind it. So after a stop, or a run that took too long (15 minutes for the tests, 45 for a search), the app restarts the sandbox, which takes under a second and keeps nothing else. If that fails, the message says the sandbox may stay busy for a few minutes.
- **The services cannot be stopped or recreated from the app during a run,** because it would cut it short. Opening the panel is still possible.

## Consequences

- Someone can see their tests run, and look for a fix, without a terminal, and cannot spend tokens by mistake or without the page being able to skip the question.
- Applying the saved fix is the next step. Until then it is applied with `docker compose exec cli healer apply /data/healer/fix.json`, which tests it again on a copy and asks before writing.
- The bridge has eighteen functions and five events.
- **Known and not solved here:** the sandbox does not notice that its client left, which also happens when someone presses Ctrl+C in a terminal, and the copy of a stopped run stays in the sandbox's memory volume until `./stop.sh` removes it. The right place to fix both is the sandbox server, and it is a separate step. The restart only keeps the sandbox from staying busy.
- Not done: choosing which error to fix (`healer run --error N` fixes the first), the number of attempts, or running a different test command. The app uses the system's defaults.
- Measured with the real app (Electron 45.3.2, Ubuntu with GNOME) and the real commands, in an isolated Compose project with its own containers, volumes and ports, and a fake Anthropic API on this computer reached through `ANTHROPIC_BASE_URL`, so no token was spent and no real key was used:
  - The real `healer test` ended with exit 1 on a project with a failing test, and the app showed the failure and the diagnosis. The `healer run --no-apply --save` search found the fix with the fake API, saved a patch of one edit in the data volume, left the project's files as they were, and put nothing new in its folder. The same error asked again was answered from the local cache with 0 tokens: the fake API had received one request in all.
  - With a container with no key, an error not stored made the system say `ANTHROPIC_API_KEY is not set: add it to .env and recreate the container`, and the app said to save a key in Settings.
  - Stop ended a search that waited for Claude in 0.2 seconds, with no `healer` process and no id file left in the container, and the sandbox was restarted. A test run stopped in the middle of a 40-second test left that test running in the sandbox, which the restart ended; a new run worked at once.
  - 26 checks of the page on the isolated project, with the confirmation dialog replaced in the test process by one that records the question and answers: the dialog was asked once with **Cancel** as the default and the cancel button, declining ran nothing and sent no request, accepting found the fix and showed its diff, Stop showed **Stopping…** and then the result with the warning about tokens, **Stop the services** was disabled during a run and **Open the panel** was not, the result could be closed, it stayed when changing section, and choosing a folder cleared it with its output.
  - 298 tests in 14 files pass, and eight changes that break a rule on purpose were each caught by a test: allowing the patch to be applied, not asking, not freeing the sandbox, saving the patch in the project, allowing two runs, not hiding a key, accepting another folder, and running after a refusal.
- Not measured: the confirmation dialog itself, which is Electron's and was replaced in the test, a real answer from Claude, a run against the services of the person who built this (they were not touched), and the 15 and 45 minute limits, which are covered by tests with fakes only.
