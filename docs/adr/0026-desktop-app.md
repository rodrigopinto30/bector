# 0026. A desktop app: a window and the key

## Context

Using the system meant cloning the repository, running `./start.sh`, putting the Anthropic key in `.env` by hand and working from a terminal. Someone who only wants to use it could not. A desktop app was asked for, where the user enters their Anthropic key, the system recognizes it, and it can be used. Docker stays, and Linux is the first system (decided with the owner). The app arrives in stages: this one is the window and the key. Choosing a project and fixing from the app, and installers, come later.

## Decision

- **Electron, in `desktop/`, written in TypeScript.** The panel is already a web page, the project already uses TypeScript and Node tooling, and Electron has an API for secrets. It adds a large dependency. Tauri would be lighter, but adds Rust.
- **A shell over the existing system, not a replacement.** The app starts and stops the services with the project's own `start.sh` and `stop.sh`, and shows the panel in a window. The sandbox, the broker and the panel are unchanged, so every guarantee of ADR 0015 and 0020 stays.
- **Docker is checked, never installed.** The app runs `docker --version`, `docker info` and `docker compose version` and tells a plain cause for each failure: not installed, not running, user not in the docker group, Compose missing. It gives the command to run and never runs `sudo` itself: `start.sh` would ask for a password in a place where nobody can answer.
- **The key is recognized in two steps.**
  1. Anthropic accepts it: `GET https://api.anthropic.com/v1/models?limit=1`, the same call the Python SDK makes to list models, which spends no tokens. 200 is valid; 429 means accepted but limited (the key is checked before the rate limit); 401 invalid; 403 refused; other statuses and network failures are told as such. The key goes to that one URL, as a header, and never into an error or a message. Text that does not look like a key (`sk-ant-` and at least 20 more characters) is not sent anywhere. Only a key that works is saved.
  2. The system sees it: after starting, the app asks the cli container whether `ANTHROPIC_API_KEY` is set, with a command that answers `set` or `unset`, never the value.
- **The key lives in the secret store of the system.** It is encrypted with Electron's `safeStorage` and kept in a file of `userData` with mode 600, written in one step. On Linux, Electron falls back to plain text when there is no secret store (backend `basic_text` or `unknown`). The vault refuses to save then, and says to install and unlock gnome-keyring or KWallet. The app goes on without a key, with the cache and the team's fixes.
- **The key reaches the containers through the environment of one process.** `docker-compose.yml` gets one line, `ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}`, in the environment shared by `cli`, `listener` and `panel`. The app runs `start.sh` or `docker compose up -d` with that variable set. Checked with fake values in an isolated project: the process variable wins over `.env`; without it, `.env` is used as before; and no process has the key in its arguments. Every line of output the app shows has the key replaced by `[hidden]`.
- **Changing the key needs a restart,** because a container gets its environment when it is created. The page says so and asks, and `start` can be asked to recreate the services even when they run.
- **One window, with a title bar and a menu of its own.** The window opens maximized and has no frame of the system: its page draws the title bar, with the name on the left and the minimize, maximize and close buttons on the right, as in most programs, and a side menu with the sections Panel and Settings. The menu collapses to icons or expands to show their names, and the choice is remembered. A section is shown in the same window, never in a new one. The system's menu bar is not used. Nothing in the frame is animated and the scrollbar space is always reserved, so changing section moves nothing.
- **The panel is a separate view, placed over the content area, with different trust.**
  - The page of the window loads only its own file, through a preload bridge of eleven functions and four events. It has `contextIsolation`, `sandbox`, no Node, no navigation, no new windows and no webviews. The main process answers its requests only if they come from the top frame of that exact page, checks each argument, and never returns or throws the key. The page can only see the key masked, as `sk-ant-…ab12`.
  - The panel is a `WebContentsView` with no bridge at all: it shows text from other computers, so nothing of the app can be reached from it. It can navigate only to the panel's own address, and may open in the browser only the Anthropic console and Docker's install guide, over https.
  - The page tells the app where its content area is, and the app puts the panel exactly there. The numbers are checked (four numbers from 0 to 20000, rounded) and cut to fit inside the window. A view of the window is drawn above its page, so the menu cannot overlap the panel, and it cannot follow an animation without lagging: that is why the layout is not animated.
  - A page that fails to load still ends in an error page that Chromium reports as finished, so the app counts the panel as loaded only if it stopped without failing. If it fails, the page says the panel is not running and takes the user to Settings, and asking for the panel again loads it again.
  - Both refuse every permission request.
- **The message about the last attempt with the key lasts only while it is the latest news.** It goes when the user moves to another section, starts typing another key or presses its close button, never while a key is being checked, and an empty field is answered with a message instead of nothing. Found in use: after a wrong key, the message stayed for ever, including after going to another section and back, so the result of the next attempt could not be told from it. Then the cross that marked an error was taken for a button that did not work. The state icons are now drawn lines (tick, triangle, circle with `!`, dots), each with its own shape and an accessible name, and none is a cross: the only cross of a message is its close button. The button says "Checking…" and the field is locked while it works. A key Anthropic does not accept is told at once, without asking the secret store anything.
- **A secret store that does not answer does not block the app.** A locked keyring waits for a password with no end, and Electron's check never returned. Found in use, with the keyring locked: the app stayed on its first screen for ever. Now each call to the secret store has a limit of 15 seconds, then the key card says that it did not answer and to unlock it, with a **Check again** button. The key is checked in parallel with Docker and the services, so it never holds the first screen back, and starting the services with a key that cannot be read says so instead of starting without it.
- **The page is built to a single file with a policy made for it.** `desktop/scripts/inline.mjs` inlines the script and the styles and writes a Content-Security-Policy that allows exactly those two by their SHA-256, with `default-src 'none'` and `connect-src 'none'`. The build fails if the script would import another file or close its own tag. Tests check that the page builds no markup from text, and that the template has no inline handlers.
- **Tools in a container, and the Electron program only with consent.** `./desktop.sh` runs the checks, the audit and the build in the pinned Node image, from `desktop/package-lock.json`, with install scripts off. Electron's own program, about 270 MB once unpacked, is a download from outside, so it is a separate command, `./desktop.sh electron`, that says what it downloads and asks first. CI and the pre-commit hook need only Electron's types.
- **The logic is kept out of Electron, so it can be tested.** Checking Docker, the key, the vault, the services, the policy of the window, its layout and the load of the panel, and the handlers receive what they need as parameters, and are covered by tests with fakes. Only the code that opens the window needs Electron to run.
- **One version, now in seven places:** the Python package and the code, and the panel and the desktop app, each with its lock. The test of ADR 0024 checks all of them.

## Consequences

- Someone with Docker can set the system up from a window: enter the key, see that it works, start, and see the panel. No terminal, no `.env`.
- The key stays out of `.env`, of the disk as text and of every command line. It does appear in the environment of the containers, visible to anyone who can run `docker inspect`, which is who could already read `.env`.
- The page holds the key for a moment, between typing and sending it. It is cleared from the field as soon as it is sent.
- Not yet done:
  - **Choosing a project and fixing from the app.** The project still goes in `workspace/` and `healer run` still runs in the terminal. When the app applies a fix, the confirmation must come from its own window, never from the panel's page, so the rule of ADR 0025 holds.
  - **Installers and updates.** The app runs from the project's folder, found through `HEALER_HOME` or by looking above its own files.
  - **Other systems.** `start.sh` installs Docker only on Linux, and Docker Desktop has other conditions.
  - **A way without Docker.** It would need another sandbox for the tests.
- The first start builds the images, which takes minutes. The window says so and shows what the build prints.
- A key typed in the terminal into `.env` and a key saved in the app can differ: the app's wins while it runs the services. Removing the key from the app restores the one in `.env`.
- Measured with the real app on this machine (Electron 45.3.2, Ubuntu with GNOME, Wayland and X11):
  - The secret store was `gnome_libsecret`: a test value was encrypted and decrypted again, and what was encrypted did not contain the text.
  - With the services already running, the window opened maximized on the panel: it covered the work area of the screen, the three window buttons were at its right edge, and the panel view had exactly the size of the content area, 1616 by 1007 pixels on a 1920 by 1080 screen. The panel had no bridge, no `require` and no `process`.
  - Changing between Panel and Settings and collapsing or expanding the menu left the title bar, the menu and the content area at the same place. Restoring and maximizing again with the real buttons moved the panel view to follow the content area every time. The button changed its name between Maximize and Restore.
  - The Settings section showed Docker 27.2.1 ready, no key saved, and the services running with a key set in `.env`. That last case led to a clearer card: "The services already have a key".
  - With the answer of Anthropic simulated (200, then 401), a made-up key was saved: the page said "Key saved" with the masked key and that the services must restart, the field was emptied, the key was nowhere in the page, and the services card offered to restart with the new key. A refused key said "The key was not saved" and left the saved one. Removing it said "Key removed" and the file was gone. Only the call to Anthropic was simulated: the secret store and the page were the real ones, and the services were not restarted.
  - A failed load of the panel (forced in the app's own view) showed "The panel is not running", and asking for the panel again loaded it. This was a bug the first time: the error page counted as loaded.
  - With the keyring locked, the app decided its first section in under two seconds, and the key card changed to "The secret store did not answer" with **Check again** after about 15 seconds.
  - With the secret store silent, text that is not a key and a key that Anthropic refuses were answered at once, and a good key after 15 seconds with "The key works, but it was not saved". Before, each took 15 and 30 seconds. Using real paste and click events, the message of a wrong key was gone after going to another section and back, and after typing; the button said "Checking…" while it worked; and an empty field said "There is no key to check".
  - The window refused to navigate away and to open new windows. Its bridge refused four links outside the allowed list, text that is not a key and an object where a key was expected.
  - The Content-Security-Policy blocked an injected script, an injected style and a request to another site.
  - Closing from the title bar closed the app. Nothing of this touched the containers.
  - Not measured:
    - Saving a real key and starting the services with it, which needs a key and recreates the containers. The logic is covered by tests with fakes, and the mechanism by the isolated check above.
    - Dragging the title bar, resizing from the edges and double-clicking the bar to maximize. They need the mouse on a real screen, and are in the testing guide as manual steps.
    - An animation of the menu, because the window was covered during the checks and animations do not advance then. It was removed for the reason above.
