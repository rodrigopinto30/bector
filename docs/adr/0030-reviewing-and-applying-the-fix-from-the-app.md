# 0030. Reviewing and applying the fix from the desktop app

## Context

The Fix section of the desktop app (ADR 0028) runs the tests and looks for a fix, and only saves it. To apply it, someone had to open a terminal. This is the last step of stage 2 of the app, and the first one that writes to the project, so the rule of ADR 0025 matters most here: what changes files is confirmed in the app's own window, never in the panel's page.

## Decision

- **Review first.** **Review the fix** reads the saved fix, in the cli container, and shows its description and, for each change, the file with the lines it takes out (`-`) and the lines it puts in (`+`). Nothing is changed by looking. The saved fix is a list of search-and-replace edits, and that is what is shown: the unified diff of the tested copy is printed in the log by the search. The text is read with strict limits (at most 100 edits, 100,000 characters on each side, a path of 1,000 characters), and what does not fit them is not shown. This reading is only for showing: what is applied is the system's own reading of the same text.
- **The page gives back only an id.** The id is the SHA-256 of the exact text that was shown. To apply, the page sends that id, and the handler accepts only 64 lowercase hexadecimal characters. The page cannot give a patch, a path or an option.
- **What is applied is exactly what was reviewed.** The main process reads the saved fix again and compares its id with the one it was given. If another fix has been saved meanwhile, for example by someone looking for a fix in a terminal, nothing is applied and the user is asked to review again. When it matches, the main process gives the system that same text through its standard input (`healer apply - --yes`), so the system never reads the file again and nothing can change the fix between the check and the application.
- **The question is the main process's, in a dialog of the app, and it is always asked.** **Cancel** is the default and the one Escape answers. The dialog says how many files change, in which folder, which files, that the system tests the fix again on a copy first and writes only if the tests pass and the files are as they were when it was tested, and that it keeps no copy of the originals. Unlike looking for a fix, it is asked even when the services have no key, because this one writes to the project.
- **The system does the application, and its exit code is read as it defines it.** `healer apply` tests the patch on a copy and writes all the edits or none: it computes them in memory first, and restores what it wrote if a write fails. Exit 0 means it was applied, and the saved fix goes. Exit 1 means the tests do not pass with the fix now, so nothing was written, and the fix stays. Anything else is an error, such as a text to replace that is no longer in the file, and its `error:` line is shown; the fix stays.
- **Applying cannot be stopped.** It is over in a moment, and a signal in the middle of the writing is the one thing that should not happen. The page shows no **Stop** while it applies, and the main process ignores a request to stop it.
- **The saved fix belongs to the project it was found for.** Choosing another folder, or going back to the default one, removes it, and the page forgets its review. It is not removed while something runs.
- **The bridge has twenty functions and five events.**

## Consequences

- Stage 2 of the app is complete: choose the project, run its tests, look for a fix, review it and apply it, without a terminal.
- The system keeps no copy of the originals, so undoing an application is the job of the project's version control. The dialog says so.
- The saved fix is not tied to a folder in the data volume: if the services are restarted from a terminal on another folder, the app does not notice that the fix was found for the first one. It is still safe, because every edit must find its text exactly once in the file, and the tests run on a copy before anything is written.
- Not done: choosing which error to fix, the number of attempts, or a different test command.
- Measured with the real app (Electron 45.3.2, Ubuntu with GNOME) and the real commands, in an isolated Compose project with its own containers, volumes and ports and a fake Anthropic API on this computer, so no token was spent and no real key was used:
  - The real `healer apply - --yes`, with the patch on its standard input through `docker compose exec -T`, exited 0 and changed the file when the tests passed; exited 1 and changed nothing when a patch left the tests failing; and exited 2 with a reason, changing nothing, for a text that is not in the file and for a path that leaves the project.
  - 31 checks of the real window, with the confirmation dialog replaced in the test process by one that records the question and answers. The review showed the description, the summary, the file and the signed lines, and changed nothing; **Close** hid it and **Review the fix** came back; the dialog was asked once, with Cancel as the default, naming the file and the folder; declining changed nothing and the review stayed; with the saved fix replaced after the review, accepting applied nothing and asked nothing more, and said to review it again; the other fix, reviewed and accepted, left the tests failing, so it was not applied and the file was as it was; a fix that did not fit the file showed the system's reason and changed nothing; the right fix, accepted, changed the file to the one line it should, left nothing else in the project, removed the saved fix and its **Review the fix** button, showed the system's verdict and `applied` line in the log, and the tests then passed; and choosing a folder removed a saved fix and its button.
  - 367 tests in 15 files pass, and ten changes that break a rule on purpose were each caught by a test: applying a fix that was not reviewed, applying without asking, making the program read the file again, keeping the fix after applying it, taking a failing run for an application, allowing a stop during the application, forgetting while a run is going, letting the page give any id, not giving the program its input, and not forgetting when the project changes.
- Not measured: the confirmation dialog itself, which is Electron's and was replaced in the test, a real answer from Claude, and an application on the services of the person who built this (they were not touched).
