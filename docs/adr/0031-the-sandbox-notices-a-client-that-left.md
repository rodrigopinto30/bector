# 0031. The test sandbox notices a client that left

## Context

The test sandbox answers one request at a time (ADR 0015 and the sandbox server's own docstring). It did not notice that the cli had gone: when someone pressed Ctrl+C in a terminal, or the **Stop** of the desktop app (ADR 0028) ended the cli, the sandbox went on with the command it was running, in the copy, until the tests ended or reached their own time limit, 300 seconds by default. Measured with the real system, its `pytest` was still running 12 seconds after a stop. Whoever came next waited behind it, and the copy stayed in the sandbox's memory volume until `./stop.sh` removed the volume. The app worked around it by restarting the sandbox after every stop, and ADR 0028 left the right fix as a separate step. This is that step.

## Decision

- **The sandbox watches the connection while a command runs.** The cli sends its request and waits for the answer, and sends nothing else, so the sandbox asks the connection, without reading from it, whether the other end was closed. When it was, the command and its children are killed like on a timeout (the same process group, and the same clean-up of what the command left behind), a `RunAbandonedError` is raised instead of a result, and nobody is answered. The question is asked every 0.2 seconds by the runner, so a run stops within a fraction of a second of the client leaving.
- **A client that only closes its writing half has not left.** Some clients, and one of the tests, shut down their writing side after sending the request and then wait for the answer. On a Unix socket the hang-up is reported only when the other end was closed altogether, while a half-close is reported as a different event, so only the hang-up counts. Checked with a socket pair: no change with data pending or after a half-close, and gone after the close.
- **A request whose client left while it waited is not run.** The check is also made before the command starts, so a request that waited behind another one, whose client left meanwhile, is not run at all.
- **The copy of an abandoned run is deleted.** It is deleted after it has been handed back, as the cli container's user, who owns it again by then: the sandbox server runs as root without the capability to override file permissions, so it cannot delete what another user owns. First the permissions are made writable, because a run can leave folders that cannot be entered or written, and then the folder is removed. A command that fails is written in the log, with its reason, because it used to be silent.
- **A stale copy is deleted after the next request.** The sandbox also deletes, when it starts and after each request, the copies that nobody used for longer than any run can last, twice the longest time limit a request may ask for (two hours). A client waits at most its time limit plus 30 seconds for an answer, so a request that is alive never has a copy that old. They are what a cli leaves if it dies before its request reaches the sandbox, which no watching of a connection can see, or what a failure here leaves behind. Only folders with the name of a copy, that are not links, are looked at. It is not done while a request runs, and a copy in use is never old.
- **The app is not changed.** **Stop** still restarts the sandbox after ending the run. The sandbox runs the code baked into its image, so a sandbox built before this change still needs the restart, and restarting a stopped sandbox keeps nothing else. It can be dropped in a later release, once everyone has rebuilt. Getting this change needs a rebuild: `./stop.sh && ./start.sh`.

## Consequences

- Ctrl+C, and **Stop** in the app, free the sandbox at once, whichever signal ends the cli, and nothing is left in the memory volume by a run that was seen.
- The restart of the sandbox that the app does after a stop is now only a safety net.
- A cli that is killed after it created its copy but before its request was sent leaves a copy that is deleted only after two hours, and only after the next request.
- Not done: the cli's own message when it is stopped, `Could not fully remove sandbox ...`, which it prints because it tries to delete the copy while the sandbox still owns it. The sandbox then deletes it, so the message is harmless, and it is the cli's to change.
- Measured with the real sandbox, rebuilt from this change in an isolated Compose project with its own containers and volumes (the services of the person who built this were not touched):
  - With a test that sleeps, the cli was stopped with Ctrl+C: the `pytest` of the sandbox was gone 0.1 seconds after the signal, and 0.5 seconds on the final build, and the copies volume was empty. Killing the cli at once, with no chance to clean up, gave 0.2 seconds, and the copies volume was empty.
  - With a second run waiting behind the first, the second client left: its request was not run. Then the first client left, and a new run was served at once: 3.9 seconds in all, 1.3 of them the tests themselves.
  - Seventeen further rounds, half with each signal and with random delays, left nothing in the sandbox. A copy was left once in the first round of the waiting case and could not be reproduced; the log of a failed deletion and the deletion of stale copies are there for that.
  - Two stale copies, one owned by the sandbox's user with a folder that cannot be written and one owned by the cli's user, were deleted after the next request, and a copy of an hour ago was kept.
  - 743 tests pass, with 96.34% of the code covered, and thirteen changes that break a rule on purpose were each caught by a test: taking a half-close for leaving, not checking before the run, not stopping the run, not deleting the copy, not cleaning up after an abandoned run, not making folders writable, not killing the children, sweeping a fresh copy, following a link, sweeping another name, not sweeping when it starts, not sweeping after a request, and not telling a failed deletion.
- Not measured: a cli that dies between creating its copy and sending its request, which is covered by the sweep and by tests, but was not made to happen with the real system, and a computer under load, where the 0.2 seconds of watching may be longer.
